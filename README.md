# КультВыезд

Цифровой ассистент для классных руководителей и родителей внутри мессенджера **MAX**.
Автоматизирует организацию школьных культурных выездов: подбор события по «Пушкинской
карте», цифровое согласие родителей (ПЭП), контроль готовности класса («Светофор») и
автоматическую сборку пакета школьных документов (приказ + приложения).

Трек: **«Досуг и развлечения»** (Минобрнауки России × MAX).

---

## 1. Назначение решения

Снять с учителя бюрократическую рутину, а с родителя — лишние действия при организации
внеклассного культурного выезда. На один выезд учитель сегодня тратит 3–6 часов
(бумажные согласия, списки, приказ, инструктаж) и получает до 150 сообщений в чате класса.

Сервис решает **один сквозной сценарий**: *каталог события → публикация в чате →
согласие родителя в 1 клик → контроль готовности → автогенерация приказа*.

Ключевые принципы:
- **Сервис не касается денег.** Оплата билета — напрямую в кассу/на сайте учреждения
  культуры (снятие риска «школьных поборов», 273-ФЗ).
- **Модельные данные обозначены явно.** Каталог — снапшот PRO.Культура.РФ (поле `source`).
- **MAX — среда взаимодействия.** Основной сценарий проходится внутри чат-бота и
  мини-приложения MAX.

**Работающее решение в MAX:** чат-бот **@t158_hakaton_max_bot** (`https://max.ru/t158_hakaton_max_bot`).
Мини-приложение подключается к этому боту (кнопка «Открыть приложение»).

## 2. Основной пользовательский сценарий

1. **Учитель** открывает мини-приложение (из бота), видит каталог и демо-класс.
2. **Каталог** (`UC-2`): фильтры «Пушкинская карта» / возраст / бесплатные → выбор события.
3. **Создание выезда** (`UC-3`): дата, время сбора/возвращения, дедлайн; участники класса
   добавляются автоматически со статусом «ожидает».
4. **Родитель** (`UC-4`) получает карточку/напоминание в MAX и нажимает
   «✅ Отпускаю ребёнка» (или «❌ Не сможет поехать» + причина). Согласие фиксируется с
   датой, временем и подписантом (ПЭП).
5. **Билет** (`UC-5`): родитель переходит по ссылке на билетный шлюз музея и отмечает
   «Билет куплен» (учёт только статуса, без денег).
6. **Контроль** (`UC-6`): дашборд «Светофор» (🟢 готов / 🟡 ждём билет / ⚪ нет ответа /
   🔴 отказ); кнопка «Напомнить не ответившим» → точечные пуши в личные диалоги.
7. **Документы** (`UC-7`): «Сформировать приказ» → скачивается DOCX (и PDF) с приложениями
   (список участников, реестр цифровых согласий, лист инструктажа по ТБ и ПДД).

## 3. Состав и архитектура решения

Модульный монолит: два контейнера, логически разделённые на ядро и адаптеры.

```
   MAX (клиенты: мобильный / веб)
        │  long polling или webhook         │  кнопка open_app (Webview)
        ▼                                   ▼
┌───────────────────────────────┐   ┌──────────────────────────────┐
│  backend (FastAPI)            │   │  miniapp (React + MAX UI)    │
│  • REST API ядра  /api/v1/*   │◄──┤  • каталог, «Светофор»       │
│  • MAX Bot Adapter            │   │  • MAX Bridge (window.WebApp)│
│  • генератор документов       │   │  • nginx + прокси /api       │
│  • SQLite (данные)            │   └──────────────────────────────┘
└───────────────────────────────┘
```

| Компонент | Технологии | Роль |
|---|---|---|
| **backend** | Python 3.12, FastAPI, SQLModel, SQLite; `python-docx`, `reportlab`, `openpyxl` | REST API ядра, адаптер MAX Bot API, генерация документов, бизнес-правила |
| **miniapp** | React 19, TypeScript, Vite, `@maxhub/max-ui`, nginx | Интерфейс учителя и родителя внутри MAX, интеграция через MAX Bridge |
| **MAX Bot API** | `https://platform-api2.max.ru` | Приём обновлений (long polling / webhook), отправка сообщений и клавиатур |

Ключевые модули backend: [`app/main.py`](backend/app/main.py) (API), [`app/bot.py`](backend/app/bot.py)
(сценарии бота), [`app/services.py`](backend/app/services.py) (бизнес-правила, «Светофор»),
[`app/documents.py`](backend/app/documents.py) (приказ), [`app/max_client.py`](backend/app/max_client.py)
(клиент MAX), [`app/catalog_seed.py`](backend/app/catalog_seed.py) (модельные данные).

Официальная спецификация MAX Bot API сохранена в [`docs/max/max-bot-api-schema.yaml`](docs/max/max-bot-api-schema.yaml).

## 4. Запуск всех локальных компонентов (одна команда)

```bash
docker compose up --build
```

Сборка занимает **~1 минуту** (лимит хакатона — 5 минут). После старта:

| Адрес | Что это |
|---|---|
| http://localhost:8080 | мини-приложение (интерфейс учителя/родителя) |
| http://localhost:8080/docs | Swagger / OpenAPI ядра |
| http://localhost:8080/openapi.json | спецификация OpenAPI 3.1 |
| http://localhost:8000/docs | Swagger напрямую на backend |
| http://localhost:8080/healthz | проверка живости |

Перед запуском скопируйте `.env.example` в `.env` (секреты см. раздел 6).

## 6. Необходимые параметры окружения и переменные

Все переменные описаны в [`.env.example`](.env.example). Секреты передаются **только**
через окружение; в репозитории их нет (п.8 ограничений).

| Переменная | Обяз. | Значение по умолчанию | Назначение |
|---|---|---|---|
| `MAX_BOT_TOKEN` | для бота | — | токен чат-бота MAX |
| `MAX_BOT_MODE` | нет | `polling` | `polling` / `webhook` / `off` |
| `MAX_API_BASE` | нет | `https://platform-api2.max.ru` | домен API MAX (актуальный) |
| `MAX_BOT_USERNAME` | нет | `t158_hakaton_max_bot` | ник бота для диплинков/кнопок |
| `MAX_WEBHOOK_URL` / `MAX_WEBHOOK_SECRET` | для webhook | — | адрес и секрет вебхука |
| `MAX_CA_BUNDLE` | нет | `/certs/ca-bundle.pem` | PEM сертификатов Минцифры |
| `MAX_TLS_INSECURE` | нет | `0` | `1` — отключить проверку TLS (только демо) |
| `DATABASE_URL` | нет | `sqlite:////app/data/kultvyezd.db` | строка подключения к БД |
| `MINIAPP_BASE_URL` / `PUBLIC_BASE_URL` | нет | `http://localhost:8080` | базовые адреса для ссылок |
| `AUTO_SEED` | нет | `true` | сидирование модельными данными при старте |
| `LOG_LEVEL` | нет | `INFO` | уровень логов |

> **Сертификаты Минцифры.** MAX использует сертификаты Минцифры; если контейнеру не
> доверяет им, обращения к API падают с `CERTIFICATE_VERIFY_FAILED`. В репозитории лежит
> готовый [`certs/ca-bundle.pem`](certs/ca-bundle.pem), монтируется в контейнер как `/certs`.
> Диагностика: `python3 scripts/doctor.py`.

## 7. Зависимости

Файлы зависимостей с зафиксированными версиями:
- backend: [`backend/requirements.txt`](backend/requirements.txt);
- мини-приложение: [`miniapp/package.json`](miniapp/package.json) + `package-lock.json`
  (создаётся `npm install`, линкуется в образ через `npm ci`).

Заметки по совместимости:
- `sqlalchemy==2.0.35` — пин, т.к. более новые версии ломают резолвинг связей в SQLModel 0.0.22;
- `miniapp/.npmrc` содержит `legacy-peer-deps=true`, т.к. `@maxhub/max-ui` объявляет
  несуществующий точный peer `react@19.2.8` (используется React 19.3.0).

## 8. Внешние сервисы и интеграции

| Сервис | Тип | Статус в MVP |
|---|---|---|
| **MAX Bot API** (`platform-api2.max.ru`) | реальная интеграция | ✅ подключено: long polling + отправка сообщений/клавиатур, webhook-эндпоинт |
| **MAX Bridge** (`st.max.ru/js/max-web-app.js`) | реальная интеграция | ✅ подключено в мини-приложении (данные пользователя, платформа, нативное скачивание файлов) |
| **Каталог PRO.Культура.РФ / «Пушкинская карта»** | модельные данные | ⚠️ снапшот каталога (поле `source`), реальный API требует доступа |
| **Билетные шлюзы музеев** | внешние ссылки | ✅ ссылка на кассу; сервис деньги не обрабатывает |
| **СМЭВ / Госуслуги, ФИАС** | перспектива | ❌ не в MVP (описано в материалах масштабирования) |

## 9. Описание работы с данными

- **Хранилище:** SQLite (файл в volume `kultvyezd-data`), схема создаётся автоматически
  при старте ([`app/models.py`](backend/app/models.py)).
- **Сущности:** класс → ученики → контакты родителей; выезд → участники (согласие, билет);
  журнал согласий (ПЭП) и артефакты документов.
- **Происхождение данных:** каталог — модельный (п.10 ограничений), это явно указано в
  каждом событии (`source`) и в `GET /api/v1/meta` (`dataset.is_mock: true`).
- **Персональные данные:** ФИО детей, дата рождения, телефон родителя — только демо-данные.
  В проде требуется согласие на обработку ПДн и шифрование.
- **Фиксация согласия:** при подписании пишется запись в журнал `ConsentAudit`
  (кто, когда, телефон, источник: bot/miniapp/api).

## 11. Пошаговый сценарий проверки

### Автоматически (рекомендуется)

```bash
# 1) тесты ядра (13 тестов)
cd backend && python3.13 -m venv .venv313 && ./.venv313/bin/pip install -r requirements.txt
./.venv313/bin/python -m pytest -q && cd ..

# 2) сквозной сценарий бота через эмулятор протокола MAX (14 шагов)
./backend/.venv313/bin/python scripts/e2e_agent.py

# 3) стек в Docker (18 шагов по HTTP)
docker compose up -d --build
python3 scripts/e2e_docker.py http://localhost:8080
```

### Вручную (через mini-app)

1. `docker compose up --build`, открыть http://localhost:8080.
2. Вкладка **«Каталог событий»** → отметить «Пушкинская карта» → «Выбрать событие» →
   «Создать выезд». Ожидаемо: переход во вкладку «Выезды класса», появляется карточка выезда.
3. В **«Светофор»** нажать «Напомнить не ответившим» — сообщение о количестве адресатов.
4. Нажать **«Сформировать приказ (DOCX)»** — скачивается файл `Приказ_выезд_<id>.docx`
   (при открытии вне MAX — обычная загрузка браузером).
5. Открыть http://localhost:8080/docs и выполнить `POST /api/v1/excursions/{id}/consent`
   со статусом `APPROVED` — статус ребёнка в «Светофоре» станет 🟢/🟡, повторный вызов вернёт
   `changed: false`.

### В живом MAX

Найти бота **@t158_hakaton_max_bot**, нажать «Начать» — ожидаемо приветствие и кнопки.
Подробности ручных шагов, которые нельзя автоматизировать, — в [`qa/manual-qa.md`](qa/manual-qa.md).

## 13. Известные ограничения

- Нет аутентификации/ролей на REST API (демо-окружение). В проде — валидация `initData`
  MAX Bridge (`hash`, `auth_date`).
- Каталог — модельный снапшот, автообновления нет.
- Юридическую выверку текста приказа должен пройти юрист школы.
- Long polling ограничен по скорости и сроку хранения событий — для продакшена
  предусмотрен режим `MAX_BOT_MODE=webhook` (эндпоинт `/webhook/max`).
- Полный список ручных проверок: [`qa/manual-qa.md`](qa/manual-qa.md).
