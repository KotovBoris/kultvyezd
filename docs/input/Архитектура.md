## 1. ОБЩАЯ СХЕМА СИСТЕМЫ (HEXAGONAL / PORTS & ADAPTERS)

Ключевая архитектурная идея — **отвязать бизнес-логику домена от платформы MAX**. MAX рассматривается лишь как один из каналов доставки (transport layer).

## 2. КОМПОНЕНТЫ СИСТЕМЫ И ЗОНЫ ОТВЕТСТВЕННОСТИ

### 2.1. Core Backend (Ядро системы)
* **Назначение:** Единственный источник правды (Single Source of Truth) для всей бизнес-логики, состояний и данных. Не зависит от библиотек мессенджера MAX.
* **Предлагаемый стек (на выбор агента):** Python (FastAPI) или Node.js (NestJS / Express). *FastAPI предпочтителен, так как генерирует обязательную по регламенту спецификацию `openapi.json` автоматически.*
* **Обязанности:**
  * Обработка REST-запросов от Mini-App и Bot Adapter.
  * Валидация входных данных и авторизационных контекстов.
  * Управление транзакциями в БД.
  * Рендеринг официальных документов (PDF/DOCX).
  * Фоновый опрос или проксирование запросов к API `PRO.Культура.РФ`.

### 2.2. MAX Bot Adapter (Адаптер мессенджера)
* **Назначение:** Изолированный сервис-транслятор между протоколом чат-бота MAX и Core API.
* **Обязанности:**
  * Прием входящих сообщений, нажатий инлайн-кнопок и вебхуков от MAX Bot API.
  * Преобразование действий пользователя в чате в стандартные вызовы Core API (например: нажатие родителем кнопки `[Отпускаю]` транслируется в `POST /api/v1/excursions/{id}/consents`).
  * Форматирование ответов Core API в визуальные блоки мессенджера (текстовые карточки, инлайн-кнопки с URL на оплату).
  * Инициация точечных рассылок (пушей) должникам по команде от Core API.

### 2.3. Mini-App Frontend (Веб-интерфейс учителя)
* **Назначение:** Высоконагруженный визуальный интерфейс, где формат чата неэффективен (каталог событий, табличный дашборд класса «Светофор»).
* **Предлагаемый стек:** React + TypeScript + библиотека компонентов `MAX UI Kit` + `MAX Bridge SDK`.
* **Обязанности:**
  * Запуск внутри Webview мессенджера через `MAX Bridge`.
  * Прямое обращение к Core Backend по REST API (минуя Bot Adapter).
  * Отображение каталога событий с фильтрами («Пушкинская карта», возраст, дата).
  * Таблица участников выезда с динамическими бейджами статусов (зеленый / желтый / серый / красный).
  * Кнопка триггера автогенерации документов.

### 2.4. Document Generation Engine (Подсистема сборки документов)
* **Реализация:** Внутренний модуль Core Backend (библиотеки `weasyprint`, `pdfkit` для HTML-to-PDF или `python-docx` для DOCX).
* **Принцип работы:** Берется утвержденный HTML/Word-шаблон школьного приказа с плейсхолдерами (`{{school_name}}`, `{{event_title}}`, `{{student_table}}`). По запросу модуль собирает подтвержденных учеников из БД, накладывает на шаблон и отдает готовый бинарник.

## 3. БАЗОВАЯ МОДЕЛЬ ДАННЫХ (ER-РЕФЕРЕНС)

```
[Classes] 1 ──── N [Students] 1 ──── N [ParentContacts]
   │                      │
   │ 1                    │ N
   ▼                      ▼
[Excursions] 1 ──── N [ExcursionParticipants]
```

### Сущности и связи:
1. **`Class` (Класс):** `id`, `grade` (например, "8"), `letter` ("Б"), `teacher_max_id`, `school_number`.
2. **`Student` (Ученик):** `id`, `class_id`, `full_name`, `birth_date`.
3. **`ParentContact` (Родители):** `id`, `student_id`, `phone_number`, `full_name`, `max_user_id` (при наличии).
4. **`Excursion` (Мероприятие):** `id`, `class_id`, `title`, `location_name`, `event_date`, `deadline`, `ticket_price`, `ticket_sale_url`, `is_pushkin_card`, `status` (`DRAFT`, `VOTING`, `CLOSED`).
5. **`ExcursionParticipant` (Сводный статус):** 
   * `id`, `excursion_id`, `student_id`.
   * `consent_status`: `PENDING` | `APPROVED` | `REJECTED`.
   * `ticket_status`: `NOT_REQUIRED` | `WAITING_PAYMENT` | `PAID`.
   * `signed_by_phone`: телефон родителя, подписавшего согласие.
   * `signed_at`: таймстемп подписания (ПЭП).
   * `rejection_reason`: строка (если отказ).

## 4. РЕФЕРЕНСНЫЕ API-КОНТРАКТЫ (CORE REST API)

### 4.1. Управление составом класса:
* `POST /api/v1/classes/import`  
  *Принимает: multipart/form-data (.xlsx/.csv). Парсит и возвращает созданный класс со списком ID.*
* `GET /api/v1/classes/{class_id}/roster`  
  *Возвращает полный список учеников и привязанных контактов родителей.*

### 4.2. Мероприятия и каталог:
* `GET /api/v1/culture-events?city=Kazan&age=12&pushkin=true`  
  *Возвращает список событий (проксируется из кэша/API PRO.Культура.РФ).*
* `POST /api/v1/excursions`  
  *Создание события учителем: `{ class_id, event_data, deadline, gathering_time }`.*
* `GET /api/v1/excursions/{id}/dashboard`  
  *Сводка для экрана «Светофор» (прогресс-бар, список детей со статусами согласия и билетов).*

### 4.3. Действия родителей (Consent & Ticketing):
* `POST /api/v1/excursions/{id}/consent`  
  *Тело: `{ student_id, parent_phone, status: "APPROVED"|"REJECTED", reason }`.*  
  *Идемпотентный метод. Если статус уже `APPROVED`, повторный запрос возвращает текущее состояние без перезаписи.*
* `POST /api/v1/excursions/{id}/ticket-confirm`  
  *Тело: `{ student_id, ticket_number: optional }`. Переводит статус билета в `PAID`.*

### 4.4. Документы и коммуникация:
* `POST /api/v1/excursions/{id}/remind-unconfirmed`  
  *Триггерит задачу на отправку пушей родителям с незавершенным статусом.*
* `GET /api/v1/excursions/{id}/export-order`  
  *Возвращает готовый файл `Приказ_Выезд_{Дата}.pdf` или `.docx`.*

## 5. ПРАГМАТИЧНЫЕ РЕКОМЕНДАЦИИ ДЛЯ ХАКАТОНА (TIME-TO-MARKET)

Если реализация распределенной архитектуры угрожает срыву дедлайна, агенту рекомендуется применить следующие **допустимые упрощения**:

1. **Модульный монолит вместо микросервисов:**  
   Объединить `MAX Bot Adapter` и `Core Backend` в один сервис/репозиторий (например, запуск бота как фоновой асинхронной задачи внутри FastAPI через `asyncio.create_task`). В презентации на схеме показывать логическое разделение, но физически деплоить один бэкенд-контейнер.
2. **База данных:**  
   Использовать `SQLite` на этапе хакатона, если развертывание PostgreSQL вызывает проблемы с конфигурацией сети в Docker Compose.
3. **Кэш API PRO.Культура.РФ:**  
   Не делать сложную синхронизацию. Сделать сидер (seeder), который при старте приложения загружает 15–20 актуальных событий в локальную базу данных, чтобы интерфейс работал мгновенно и не зависел от сбоев внешнего шлюза во время демонстрации жюри.
4. **Безопасность (Docker):**  
   Строго вынести все токены (`MAX_BOT_TOKEN`, секреты) в `.env.example`. В коде брать значения только из `os.getenv()`.
